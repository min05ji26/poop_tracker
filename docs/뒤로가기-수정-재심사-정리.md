# 뒤로가기 수정 & 재심사 정리 (2026-09-09)

## 1. 반려 사유

> **최초 화면에서 내비게이션 바의 뒤로가기 클릭 시 미니앱이 종료되지 않아요.**
> 최초 화면에서 내비게이션 바 뒤로가기 클릭 시 미니앱이 종료되도록 구현해 주세요.

### 진짜 원인 (진단으로 확정)

**`backEvent`(뒤로가기 이벤트) 핸들러가 아예 없었던 것.**

- 이 앱은 라우터/URL 없이 **React state 로만** 화면을 전환한다 → 웹뷰 히스토리 항목은 항상 1개뿐.
- 구 버전엔 뒤로가기 이벤트를 처리하는 코드가 전혀 없었다.
- 심사자가 홈(최초 화면)에서 토스 내비게이션 바의 ‹ 를 누름 → 토스는 처리기가 없으니 "웹뷰 히스토리 뒤로가기"를 시도 → 갈 데가 없어서 **아무 일도 안 일어남(먹통)** → "미니앱이 종료되지 않아요".
- 올바른 방법: `backEvent`를 구독하고, **최초 화면이면 직접 `Screen.close()` 호출**.

## 2. 원인 분석 (생각 과정)

- **"종료 버튼을 UI에 만들어야 하나?"** → 아니다. 내비게이션 바는 토스 앱이 웹뷰 위에 직접 그린다.
  그 ‹ 를 누르면 토스가 `backEvent`를 웹뷰로 보낸다. 웹이 할 일은 **그 이벤트를 구독해서 처리**하는 것.
- 관련 API: `@apps-in-toss/web-framework` 의 `graniteEvent.addEventListener('backEvent', { onEvent })` + `Screen.close()`.
  (토스 개발자 커뮤니티가 안내하는 "진입 페이지에서 backEvent 구독 + close" 패턴과 동일)
- **중요:** `backEvent`를 구독하는 순간 토스는 기본 뒤로가기를 **완전히 차단**하고 앱에 넘긴다
  (토스 문서: "기본 뒤로가기는 차단돼요"). 그래서 화면별로 전부 우리가 처리해야 한다.

## 3. 1차 구현에서 발견한 문제 — 확인창

1차로 `backEvent` 처리 + "기록 중 뒤로가기 시 확인"을 `window.confirm()` 으로 넣었다.
→ 테스트에서 기록 화면 뒤로가기가 안 먹고, 확인창도 안 뜨고, 원래 있던 미래 날짜 `alert()` 도 사라짐.

**원인:** 토스 웹뷰에서 브라우저 기본 다이얼로그(`window.confirm`/`alert`/`prompt`)는 신뢰할 수 없다.
`window.confirm()` 이 `undefined`(falsy)를 반환 → `if (!confirm(...)) return` 코드가 항상 early return → 버튼 먹통.
토스 문서도 "브라우저 기본 다이얼로그 대신 자체 모달을 쓰라"고 안내.

**해결:** 재사용 가능한 앱 내부 모달 컴포넌트 `AppDialog` 를 만들고,
확인/알림 3곳(기록 나가기 / 기록 삭제 / 미래 날짜)의 브라우저 다이얼로그를 전부 이걸로 교체.

## 4. 2차 혼란 — "예전 버전이랑 뭐가 달라진 거야?"

새 빌드를 폰에 올려 테스트했는데, **홈에서 ‹ 를 눌러도 예전이랑 똑같아 보였다.**
"홈 화면에 뒤로가기 버튼을 따로 만들어야 하나?" 하는 의심까지 나왔다.

### 왜 헷갈렸나

- 라우터가 없어서 화면 전환이 URL/히스토리에 안 남는다 → 겉으로 보면 구/신 버전의 back 동작 차이가 안 보인다.
- 구 버전: 최초 화면 back = 먹통(아무 반응 없음).
  신 버전: 최초 화면 back = `Screen.close()` 로 종료.
  → 근데 "종료됨"과 "먹통"을 순간적으로 구분하기 어렵고, 테스트하다 브라우저 히스토리가 쌓이면 구 버전도 뭔가 되는 것처럼 보인다.

### 어떻게 해결(확인)했나

임시 **온화면 진단 오버레이**(`DebugOverlay`)를 넣었다.
- `backEvent` 가 발사될 때마다 화면 하단에 로그를 찍고, `localStorage` 에도 저장 → 앱이 닫혔다 다시 열려도 직전 기록이 보임.

**실기기 확인 결과:** 홈에서 내비바 ‹ 누름 → 앱 닫힘 → 다시 열었더니 하단에:

```
0시 29분 40초  screen=home → closeApp() 호출
0시 29분 40초  backEvent 수신
```

- `backEvent 수신` = 그 ‹ 버튼이 실제로 `backEvent`를 쏜다 → 구독이 올바른 접근이었음이 증명됨.
- `closeApp() 호출` = 우리 코드가 `Screen.close()`를 불렀고, **그게 앱을 닫은 것**(토스 기본동작 아님).

→ **수정이 정상 동작함을 확인.** 확인 후 진단 오버레이는 전부 제거하고 깨끗하게 재빌드.

### 화면별 뒤로가기 동작

| 화면 | 내비바 ‹ 누르면 |
|---|---|
| 온보딩 / 홈 / 로딩 (최초 화면) | **앱 종료** (`Screen.close()`) |
| 달력 | 홈으로 |
| 기록 | 달력으로 — 입력한 내용이 있으면 "입력한 내용이 저장되지 않아요. 그만둘까요?" 모달 → "그만두기" 달력 / "계속 쓰기" 유지 |

### 그 외 모달

- 기록 삭제 → "이 기록을 삭제할까요?" (빨강 확인)
- 미래 날짜 + 버튼 → "아직 오지 않은 날이에요. 오늘까지만 기록할 수 있어요."

## 6. 배운 것 / 얻은 것

1. **토스 내비게이션 바는 네이티브가 그린다.** 웹에서 바를 만드는 게 아니라 `backEvent`를 처리한다.
   최초 화면 종료는 `graniteEvent` 구독 + `Screen.close()`.
2. **`backEvent`를 구독하면 토스 기본 뒤로가기가 전부 차단된다.** 모든 화면의 back 을 앱이 직접 책임져야 한다.
3. **라우터 없이 state 로만 화면을 전환하면**, 최초 화면 back 이 기본적으로 먹통이 된다(히스토리가 1개뿐이라). → 명시적 `Screen.close()` 필요.
4. **토스 웹뷰에서 `window.confirm`/`alert`/`prompt` 쓰지 말 것.** 확인/알림은 앱 내부 컴포넌트로.
5. `history.replaceState()` / 라우터 히스토리 조작은 토스 네이티브 종료 동작을 깨뜨린다. (이 앱은 라우터 없어 무관하지만, 도입 시 주의.)
6. **로컬에서도 backEvent 테스트 가능:** `@apps-in-toss/devtools` mock 이 `backEvent`를 시뮬레이션한다.
   콘솔에서 `window.dispatchEvent(new CustomEvent('__ait:backEvent'))` → mock 의 `closeView()` 가
   `[@apps-in-toss/devtools] closeView called` 로그를 남긴다.
